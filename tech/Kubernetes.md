# Kubernetes

**Kubernetes** — *переносимая*, *расширяемая платформа* *с открытым кодом* *для управления контейнерными нагрузками и сервисами*, *поддерживающая* и *декларативную настройку*, и *автоматизацию* ([документация Kubernetes](https://kubernetes.io/docs/concepts/overview/)).

*Если* [*Docker*](../Docker.md) *отвечает на вопрос*, *как упаковать и запустить один контейнер*, *то Kubernetes* — *на вопрос*, *как держать запущенными сотни контейнеров* *на десятках машин*: *перезапускать упавшие*, *обновлять без простоя*, *направлять к ним трафик*. *Подход тот же*, *что в* [*инфраструктуре как коде*](../Infrastructure-as-Code.md#декларативный-подход): *вы описываете желаемое состояние*, *а система сама к нему приходит*.

# Компоненты

## Кластер `Cluster`, узлы `Nodes`, модули `Pods`, `Workload`
Для начала работы с Kubernetes необходимо создать *Кластер*.

**Кластер** (англ. `Cluster`) представляет собой *множество* *Узлов*.

Каждый **Узел** *представляет собой рабочую машину* (англ. `worker machine`), являющуюся *частью Кластера* и *запускающую контейнерные приложения* (англ. `containerized applications`). *Узлы* в *Кластере* *не являются частью публичного интернета*, то есть они *не общедоступны*.

На рабочих *Узлах размещаются* **Модули** (англ. `Pods`), являющиеся *компонентами приложения*, компонентами Workload.  
**Workload** (рус. `рабочая нагрузка`) - это приложение, запущенное в Kubernetes.

*В документации модуль определён так*: **модули** — *наименьшие развёртываемые единицы вычислений*, *которые можно создать и которыми можно управлять в Kubernetes* ([документация Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/)). *Обычно в модуле один контейнер*, *но их может быть и несколько* — *тогда они делят сеть и хранилище*.

## Контрольный план

**Контрольный план** (англ. `Control plane`)
> The container orchestration layer that exposes the API and interfaces to define, deploy, and manage the lifecycle of containers.

*Проще говоря*, *контрольный план* — *это «мозг» кластера*: *он хранит желаемое состояние*, *следит за фактическим* и *раздаёт узлам команды*, *чтобы одно совпало с другим*.

# Как запустить приложение

## Развёртывание (Deployment)

*Модули руками почти не создают*: *если такой модуль упадёт*, *его никто не перезапустит*. *Вместо этого описывают* **развёртывание** (англ. `Deployment`) — *объект*, *который обеспечивает декларативное обновление модулей*. *Вы описываете желаемое состояние*, *а контроллер развёртывания* *приводит к нему фактическое* — *с контролируемой скоростью* ([документация Kubernetes](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)).

*Пример из документации*: *три копии веб-сервера* `nginx`.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
  labels:
    app: nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:1.14.2
        ports:
        - containerPort: 80
```

*Здесь сказано*, *что должно быть*, *а не что делать*: *«три модуля с таким-то образом»*. *Упадёт один* — *контроллер поднимет замену*. *Поменяете образ* — *модули заменятся постепенно*, *без остановки сервиса*.

```sh
kubectl apply -f nginx-deployment.yaml   # передать желаемое состояние в кластер
kubectl get deployments                  # посмотреть, что получилось
```

## Сервис (Service)

*Модули приходят и уходят*: *развёртывание их пересоздаёт*, *а вместе с ними меняются и адреса*. *Обращаться к конкретному модулю* *поэтому бессмысленно*.

**Сервис** (англ. `Service`) *открывает доступ к приложению*, *работающему в кластере*, *через одну постоянную точку входа* — *даже когда нагрузка разнесена* *по нескольким модулям* ([документация Kubernetes](https://kubernetes.io/docs/concepts/services-networking/service/)).

```yaml
apiVersion: v1
kind: Service
metadata:
  name: nginx-service
spec:
  selector:
    app: nginx
  ports:
  - protocol: TCP
    port: 80
    targetPort: 80
```

*Сервис находит свои модули* *по меткам*: `selector` *выше* *совпадает с меткой* `app: nginx` *из развёртывания*. *Появился новый модуль с этой меткой* — *трафик пойдёт и к нему*.

## Ingress

*Сервис открывает приложение внутри кластера*. *Чтобы до него дошёл запрос из интернета*, *нужен ещё один слой*.

**Ingress** *открывает HTTP- и HTTPS-маршруты* *снаружи кластера* *к сервисам внутри него* *и может брать на себя* *балансировку нагрузки*, *расшифровку TLS* и *маршрутизацию по доменным именам* ([документация Kubernetes](https://kubernetes.io/docs/concepts/services-networking/ingress/)).

*Важная деталь на сегодня*: *проект Kubernetes* *рекомендует использовать вместо Ingress* *более новый* **Gateway**. *API Ingress заморожен*: *он стабилен* *и удалять его не планируют*, *но и развивать больше не будут*. *Для нового кластера* *стоит начинать сразу с Gateway*.

*Именно на эту точку входа* *и указывает* [*запись DNS*](../Domains-DNS-CDN.md#зона-и-записи-dns) *вашего домена*, *а расшифровка TLS здесь* — *это та самая* [*терминация HTTPS*](../Domains-DNS-CDN.md#сертификаты-и-https), *только внутри кластера*.

## Конфигурация и секреты

*Правило то же*, *что везде*: [*конфигурация отделена от кода*](../Domains-DNS-CDN.md#общие-понятия). *В Kubernetes для этого два объекта*:

* **ConfigMap** — *объект для хранения* *неконфиденциальных данных* *в виде пар «ключ — значение»* ([документация Kubernetes](https://kubernetes.io/docs/concepts/configuration/configmap/)): *адреса*, *флаги*, *настройки*.
* **Secret** — *объект с небольшим количеством чувствительных данных*: *паролем*, *токеном* или *ключом* ([документация Kubernetes](https://kubernetes.io/docs/concepts/configuration/secret/)).

*И предупреждение из той же документации*, *о котором часто не знают*: *по умолчанию секреты хранятся* *в хранилище кластера* *незашифрованными*. *Название «Secret»* *не означает шифрования*: *его нужно включать отдельно* *и ограничивать доступ* *к этим объектам*.
